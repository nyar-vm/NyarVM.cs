# Frame 层 — 帧封装

## 定位

Frame 层是数据处理管道中"给载荷画边界"的一层。它的唯一职责是：接收一段完整的载荷字节，在前面或后面加上帧边界标记（长度前缀/分隔符），写入输出缓冲区。

## 为什么封帧器必须无状态？

封帧是一个 **纯计算**操作：给定一段载荷字节，算法始终是 "写 4 字节长度 → 写载荷" 或 "写载荷 → 写换行符"
。这里面不涉及任何需要跨调用维护的信息。

反过来说：如果有人想在封帧器里加状态，唯一合理的动机是"记住上一次写到哪里了"，但这是缓冲区的职责，不是封帧器的。
`IBufferWriter<byte>` 已经提供了缓冲能力，封帧器只管把结果写进去，不需要知道缓冲区之前写过什么。

**无状态带来的好处**：

- 线程安全免费获得，不需要 `lock`。
- 同一个 `IFramer` 实例可以被所有连接复用，零分配。
- 测试极其简单：输入 → 输出，无副作用。

## 为什么 Frame 不负责粘包？

粘包/半包是 **接收端**的问题。发送端每帧独立发出，不需要"记住上一帧还剩多少"
。把发送端的封帧器和接收端的缓冲区管理混在一起，会迫使发送端也维护一个不必要的状态机。Frame 负责封装，Unframe 负责解包——
**非对称职责**，不需要对称实现。

## 不应该承担什么职责？

- **不应做任何序列化**：封帧器不知道也不应该知道载荷里是 JSON 还是 MessagePack。载荷对封帧器是完全不透明的
  `ReadOnlySpan<byte>`。
- **不应管理缓冲区**：封帧器向 `IBufferWriter<byte>` 写入，由调用者决定何时 `flush`、何时发送。封帧器不知道底层是 Socket
  还是文件。
- **不应校验载荷合法性**：REPL 场景中载荷是 JSON 还是非法文本，不由封帧器判断。
- **不应实现任何分帧协议的高层语义**：例如 HTTP chunked 分帧有自己独立的状态机逻辑，那不是通用 Frame 层的职责。

## 与上下游的衔接

```
上游（Serialize / Project）→ 产出载荷 ReadOnlySpan<byte>
    ↓
IFramer.frame(payload, writer)  → 加上帧边界，写入 IBufferWriter<byte>
    ↓
下游（网络发送 / 文件写入）→ 调用 writer.WrittenMemory 发送
```

封帧器位于序列化器和 I/O 发送之间，是管道中最后一个"加工"步骤。它不消耗也不产生新数据——只添加前缀/后缀字节。

## 典型场景

- **TCP 消息边界**：`LengthPrefixedFramer(4)` — 每条消息前 4 字节大端长度。接收端据此切帧。
- **行协议（RESP、NDJSON）**：`DelimiterFramer("\r\n")` — 载荷末追加 CRLF。人类可读，适合 Redis 协议或逐行 JSON。
- **LEB128 紧凑前缀**：`LengthPrefixedFramer(useVarInt: true)` — 短消息 1 字节，长消息多字节。适合 MQTT、Protobuf 流式。
