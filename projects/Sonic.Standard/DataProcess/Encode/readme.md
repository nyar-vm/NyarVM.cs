# Encode 层 — 基本类型编码

## 定位

Encode 层是最底层的"类型感知"层：将 `int`、`float`、`string` 等基本类型转换为字节序列。它只处理 **单个基本类型**到其
**某一种字节表示**的规则转换，不处理任何复合结构。

## 为什么编码层只管基本类型？

如果编码器知道 "Person"，它就成了序列化器。一旦编码器承担了"字段顺序""容器格式"等职责，就失去了可替换性——你不能把一个 "写入
Person 的编码器" 换成大端编码器用于网络传输。

编码层的唯一决策是 **端序和变长策略**：

- `NetworkBinaryEncoder`：固定宽度，大端。
- `LittleEndianEncoder`：固定宽度，小端。
- `VarIntEncoder`：变长宽度，LEB128。

这三种编码器输出截然不同的字节，但上层（序列化器、投射器）通过依赖注入切换它们时，一行代码都不需要改。这正是"只管基本类型"
带来的威力。

## 为什么数据不足不在编码层出现？

编码是 **写入**操作，`IBufferWriter<byte>` 自动扩容。编码器永远不需要判断"缓冲区够不够"，这是 I/O
层的职责。相比之下，解码是读取操作，数据不足是常态，需要 `out bytesConsumed` 来表示。编码和解码的接口不对称，反映的是读写方向天然的不对称。

## 为什么编码器无状态？

基本类型编码是确定性规则：`42` 用大端编码永远是 `00 00 00 2A`，跟上下文无关。不需要状态机，不需要缓冲区，不需要记忆上次写到哪了。每个
`encode_i32` 调用都是原子操作。

无状态意味着：

- 整个应用只需要一个 `IEncoder` 实例。
- 无需 `IDisposable`，无需 `reset`。
- 线程安全自动成立。

## 不应该承担什么职责？

- **不应写入格式化骨架**：大括号、方括号、缩进属于序列化层。如果出现在编码层，就是在越权做格式化。
- **不应处理复合类型**：`List<int>` 应该由序列化层拆成"序列开始 → encode_i32 → encode_i32 → 序列结束"，编码层只看到逐个的
  `encode_i32`。
- **不应管理输出缓冲区**：编码器被动接受 `IBufferWriter<byte>`，不持有也不管理缓冲区生命周期。
- **不应做字符编码转换**：`string` 到 UTF-8 bytes 的转换在调用编码层之前已完成，编码层拿到的是 `Utf8Text`（已验证的 UTF-8
  字节）。

## 与上下游的衔接

```
上游（Serialize / Project）→ 产生具体的 int / float / string 值
    ↓
IEncoder.encode_i32(value, writer) → 按端序/变长规则写入字节
    ↓
下游（IBufferWriter<byte>）→ 接收原始字节，等待 flush
```

## 典型场景

- **网络协议头部**：`NetworkBinaryEncoder` — MQTT 的剩余长度字段、固定头中的包标识符，需要大端序。
- **本地持久化**：`LittleEndianEncoder` — x86/x64 原生端序，写入文件最快。
- **Protobuf 兼容**：`VarIntEncoder` — LEB128 变长编码，小整数 1 字节，大整数最多 10 字节。
