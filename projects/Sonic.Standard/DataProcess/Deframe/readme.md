# Unframe 层 — 帧解包

## 定位

Unframe 层是 Frame 层的接收侧对称操作：从源源不断的字节流中，按帧边界协议切出完整的帧载荷。

## 为什么解帧器必须有状态？

这是 Unframe 与 Frame 最本质的不对称。 **封帧是纯计算，解帧是状态机**。

核心原因： **网络是不按帧边界送数据的**。TCP 是字节流，你发 3 个 100 字节的帧，对方可能一次 `read` 收到 250
字节——第一帧完整、第二帧完整、第三帧只到了 50 字节。

解帧器必须：

1. 维护内部缓冲区，把不完整的帧头/帧体攒着。
2. 记住当前的解析状态：正在读长度前缀 / 正在等载荷 / 正在找分隔符。

如果解帧器无状态，这些状态就会泄漏到调用方——每一个使用解帧器的业务代码都得手写一遍粘包处理逻辑，这正是现有方案最令人痛苦的地方。

## 为什么半包不是错误？

半包是 **正常流控**，不是格式错误。当 `try_get_next_frame` 返回 `false` 时，消息是"再等等"
——更多字节还在路上。抛出异常会让调用方进入异常处理路径，而半包在每条消息的边界都会发生（想想 1GB 文件被切成 4KB 的 TCP
包，半包发生了几十万次）。

**区分流控与错误**是 Unframe 层最重要的设计决策：`false` = 等待更多数据（正常），异常 = 前缀非法（协议破坏）。

## 为什么 Span 有效期受限？

`try_get_next_frame` 返回的 `ReadOnlySpan<byte>` 指向解帧器内部缓冲区。在下一次 `unframe` 喂入新数据时，缓冲区可能扩容（数组重新分配），旧
Span 失效。

这个设计的动机是 **零拷贝**：绝大多数使用场景中，拿到帧载荷后立刻传给反序列化器消费，不需要长期持有。如果拷贝发生在解帧器内部，那就是
100% 的浪费——因为 99% 的调用者随后就反序列化掉了。

需要长期持有时，调用者显式 `payload.ToArray()`，把拷贝的决策权交给知道生命周期的调用者，而非猜不透的库。

## 不应该承担什么职责？

- **不应解析载荷内容**：载荷是 JSON 还是 MessagePack 与解帧器无关。解帧器只认识帧边界格式（长度前缀/分隔符）。
- **不应处理 TLS/压缩**：这些是中间件层的职责，应在解帧后、反序列化前插入。
- **不应管理 I/O 读取**：解帧器被动接收 `feed`，不主动读 Socket。I/O 读取循环由调用者控制。
- **不应实现应用层心跳/超时**：解帧器只管字节边界，不管时间边界。

## 与上下游的衔接

```
上游（网络读取 / PipeReader）→ 喂入 ReadOnlySpan<byte>
    ↓
IUnframer.unframe(data)           → 内部累积
IUnframer.try_get_next_frame()    → 返回完整帧载荷 / false
    ↓
下游（Deserialize / Decode）→ 消费帧载荷进行业务解析
```

## 典型场景

- **请求-响应 RPC**：`LengthPrefixedUnframer` — 先读 4 字节长度，再等 body。`try_get_next_frame` 在 body 不完整时返回
  `false`，调用方继续 `ReadAsync`。
- **Redis 协议**：`DelimiterUnframer("\r\n")` — 简单好用，一行命令一个帧。
- **传感器固件上传**：`FixedLengthUnframer(128)` — 每条记录固定 128 字节，不需要前缀。
