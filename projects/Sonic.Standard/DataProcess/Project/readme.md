# Project 层 — 类型投射

## 定位

Project 层是 DataProcess 中 **与序列化层平行的第二条路径**。序列化路径走"格式化表示"（JSON/MessagePack），投射路径走"
原始字节布局"。两条路径共享编码/解码和 I/O 层，但在"如何表示结构"上分道扬镳。

## 为什么需要第二条路径？

序列化路径自带了很大开销：JSON 的 `{"field": value}` 每次都要写键名字符串；MessagePack 的 fixmap 前缀占用 1
字节。当字段顺序固定（二进制协议）、通信双方共享 schema 时，这些开销是 **纯浪费**。

投射路径的设计动机就是消除格式开销：

- 没有键名——字段按固定顺序排列，位置即语义。
- 没有容器标记——不需要 `[` `]` `{` `}`，字段值直接首尾相接。
- 没有嵌套层级标记——编码器写 `f64` + `f64`，接收方解码 `f64` + `f64`。到哪结束？你在共享 schema 里说好了是 2 个字段。

## 什么时候用序列化路径，什么时候用投射路径？

| 决策因素                  | 序列化路径       | 投射路径                          |
|:--------------------------|:-----------------|:----------------------------------|
| 通信双方是否共享 schema？ | 不需要           | 需要                              |
| 是否需要跨语言互操作？    | JSON/MP 天然支持 | 需要双方遵守同一定义              |
| 是否需要人可读？          | JSON/XML 可以    | 不可以                            |
| 对性能敏感吗？            | 一般够用         | 极致性能                          |
| 字段顺序是否固定？        | 无所谓           | 必须固定                          |
| 能否容忍未知字段？        | 还原层可跳过     | 语义上不支持（必须同版本 schema） |

把投射路径看作"编译期约定了 ABI 的直接内存拷贝"——C 的 `struct` 写入文件就是投射，`fwrite(&s, sizeof(s), 1, f)` 不需要序列化框架。但
C struct 有对齐填充、端序问题、版本兼容问题——投射层通过注入编码器解决端序，通过字段顺序约定解决布局。

## 为什么投射器持有 IEncoder/IDecoder？

序列化器内部决定编码策略（JSON 写数字文本，MessagePack 写 fixint）。投射器没有容器格式来"包裹"编码选择——它必须显式知道
`encode_f64` 是大端还是小端。

注入 `IEncoder`/`IDecoder` 意味着：

- 同一个 `Point` 投射器，注入 `NetworkBinaryEncoder` → 网络传输用大端。
- 注入 `LittleEndianEncoder` → 本地文件用小端。
- 投射代码本身不包含任何端序逻辑。

## 不应该承担什么职责？

- **不应生成格式骨架**：如果投射器里出现了写入 `[`、`{` 的代码，说明你在用投射层模拟序列化——应该直接用序列化路径。
- **不应处理字段缺失 / 向前兼容**：投射层假设双方 schema 一致。版本兼容属于序列化路径的优势领域。
- **不应做编解码之外的任何转换**：投射层就是在写字段值，不做格式化、不做验证、不做业务逻辑。

## 与上下游的衔接

```
上游（业务层）→ 构造类型 T 的实例
    ↓
IProjector<T>.project(value, writer) → 按固定顺序投射字段值
    ↓（调用 IEncoder 写入基本类型）
下游（IEncoder → IBufferWriter<byte>）→ 写入原始字节
```

## 典型场景

- **游戏网络包**：位置同步 `(float x, float y, float z, float yaw)` —— 投射器输出 16 字节，序列化器（JSON）输出
  `{"x":1.23,"y":4.56,...}` 约 60+ 字节。帧率 60 的游戏中，带宽差异巨大。
- **嵌入式固件通信**：传感器以固定帧格式上传数据，MCU 端写 C struct，服务端用投射器还原——双方写死字节布局。
- **列式文件格式**：Parquet 的列块本质上是固定 schema 的密集投射。
