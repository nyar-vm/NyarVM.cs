# Detect 层 — 格式自动检测

## 定位

Detect 层在收到未知字节流时，通过检测链猜测其格式。它解决一个非常实际的问题： **不让你在代码里写
`if (port == 80) json else if (port == 1883) mqtt`**。

## 为什么不能用端口号/URL 推断格式？

可以，但那不是库的职责，是应用层的约定。库不应该假设"80 端口 = JSON"——你可以在 8080 端口上跑 MessagePack，也可以在
`/api/json` 路径下返回 protobuf。

Detect 层的哲学是： **数据自带格式指纹**。JSON 以 `{`、`[`、`"` 开头；MessagePack 首字节在 `0x80-0x8F` 或 `0xC0-0xC3` 范围；MQTT
固定头的高 4 位是控制包类型。这些指纹是格式固有的，不需要外部元数据。

## 为什么用置信度而非二值判断？

二值判断（`是/否`）在处理模糊边界时会出问题：

- 一段以 `{` 开头的文本，可能是 JSON，也可能是一个恰好以 `{` 开头的纯文本消息。
- UTF-8 BOM（`0xEF 0xBB 0xBF`）开头的文件，可能是 JSON、CSV、XML 或任意文本格式。

置信度允许检测器表达"我认为 80% 是 JSON，但也不排除是纯文本"。多个检测器竞争时，调用方可以：

- 选最高置信度的。
- 设置阈值（如 0.5）以下拒绝所有候选。
- 当两个检测器置信度接近时，交给用户决定。

## 为什么检测器不消费数据？

`detect` 接受 `ReadOnlySpan<byte>`，不修改、不消耗。这是关键约束——如果检测器消费了字节再发现"不是我的格式"
，被消费的字节已经丢失，后续真正的解析器会错位。

**检测器只能 peek，不能 consume**。返回 `true` 后，调用方将同一段字节完整传给反序列化器。

## 为什么检测与解帧是分离的？

检测回答"这是什么格式"，解帧回答"帧边界在哪"。两个问题独立：

- 你可以在检测出 JSON 后，用 `DelimiterUnframer("\r\n")` 切行。
- 也可以在检测出 MessagePack 后，用 `LengthPrefixedUnframer` 切帧。

格式类型与分帧协议不是一对一的关系。HTTP 的 body 可以是 JSON、可以是 XML、可以是 MessagePack——但 HTTP
的分帧（Content-Length / chunked）是一样的。

## 不应该承担什么职责？

- **不应解析内容**：检测器只看魔数/签名/首字节分布，不进入格式的深层语法。
- **不应修改数据**：纯读。检测通过后，调用方重新从零解析，不能依赖检测器"跳过了几个字节"。
- **不应做版本协商**：检测到"这是一个 HTTP 请求"不意味应该自动选择 HTTP/1.1 还是 HTTP/2。版本协商是协议层的职责。
- **不应用异常表达"不是我的格式"**：`detect` 返回 `false`，安静离场。抛出异常意味着"检测过程本身出错了"，不是"不匹配"。

## 与上下游的衔接

```
上游（网络接收 / 文件读取）→ ReadOnlySpan<byte> 未知数据
    ↓
Detect 链：JsonDetector → MessagePackDetector → MqttDetector → ...
    ↓ 选出最高置信度候选
下游（反序列化器 / 解帧器 / 扫描器）→ 按检测结果选择对应实现
```

## 典型场景

- **通用消息网关**：一个端口接收来自不同客户端的消息，根据首字节自动分发到 JSON 处理器、MessagePack 处理器或 MQTT 处理器。
- **文件格式嗅探**：用户上传文件，不确定是 CSV 还是 JSON——检测链自动识别后用对应解析器。
- **协议降级**：服务端同时支持新旧两种协议，旧协议以 `0x01` 开头、新协议以 `0x02` 开头——检测器按首字节分流。
