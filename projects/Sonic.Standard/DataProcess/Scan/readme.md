# Scan 层 — 快速字段提取

## 定位

Scan 层提供一种 **不构建完整对象树**的字段提取方式：给定一段格式化载荷（JSON、XML 等）和一个字段路径表达式，直接返回目标字段的值。它是反序列化的极致性能替代品。

## 为什么需要跳过反序列化？

反序列化路径的核心开销是 **构建对象图**：解析 JSON → 分配 `JObject`/`JsonDocument` → 遍历属性 → 分配 `Person` → 分配
`Address` → ...。这个开销在两种场景中不可接受：

1. **大文档小查询**：100MB 的 JSON 日志文件，你只关心 `$.timestamp`。完整反序列化需要将 100MB 全部解析为对象，内存峰值
   200MB+。扫描器只需在字节流中跳过无关字段，找到 `"timestamp"` 键读完值就返回——内存峰值约 1MB。

2. **高吞吐消息路由**：Kafka 消息每秒数万条，你只需要读取 `$.event_type` 来决定路由到哪个处理者。如果每条都反序列化，CPU
   消耗主要在"解析不关心的字段"上。扫描器只看头部几个字节就返回。

## 为什么扫描器不取代反序列化器？

扫描器有根本性的限制：

- **只能提取已有路径**：你知道字段叫什么、在哪一层，但扫描器不能遍历未知结构。
- **不能做业务逻辑**：扫描器返回孤立的字段值，不出产完整的业务对象。后续业务逻辑消费的是 `Person`，不是 `$.person.name`
  的字符串切片。
- **格式深度绑定**：`JsonScanner` 理解 JSON 语法，`XmlScanner` 理解 XML 语法——扫描器是格式感知的。与之相比，反序列化器依赖投影层屏蔽格式差异，类型
  T 的还原器在 JSON 和 MessagePack 之间可以复用。

扫描器和反序列化器是 **互补**关系，不是替代：

- 路由/过滤/采样 → 扫描器。
- 业务处理 → 反序列化器。

## 为什么用字符串路径而非 Lambda？

Lambda 表达式（`p => p.User.Address.City`）需要编译时知道类型结构。扫描器的典型场景是配置驱动的——路径字符串从配置文件或数据库中读取。字符串路径允许运行时动态决定提取哪个字段，Lambda
做不到。

## 不应该承担什么职责？

- **不应构建对象图**：如果扫描器内部创建了 `JObject` 或 `Dictionary<string, object>`，那就不是扫描器，是"偷懒的反序列化器"。
- **不应修改数据**：扫描器纯读，不调 `serialize`。路径即查询，查询不应有副作用。
- **不应处理二进制协议**：扫描器的工作假设是格式化的自描述数据（JSON/XML/CSV）。二进制投射协议没有键名，无法按路径扫描，直接走还原器即可。

## 与上下游的衔接

```
上游（Unframe 输出的帧载荷 / 文件内容）→ ReadOnlySpan<byte> 格式化数据
    ↓
IScanner<TResult>.scan(payload, "$.path.to.field")
    ↓ 字节级跳转，跳过无关字段，提取目标值
下游（路由逻辑 / 监控告警 / 条件判断）→ TResult 字段值
```

## 典型场景

- **日志聚合**：Elasticsearch 的 JSON 日志中提取 `$.level` 和 `$.timestamp`，统计错误率——不解析整个日志对象。
- **API 网关路由**：根据请求体中的 `$.method` 路由到不同微服务，延迟要求亚毫秒级。
- **配置热更新**：监听配置文件变更，只提取变更项的值，不重新加载整个配置。
