# Decode 层 — 基本类型解码

## 定位

Decode 层是 Encode 层的读取侧对称操作：从字节缓冲区中按规则还原基本类型。与编码层一样，解码器只处理单个基本类型，不涉及复合结构。

## 为什么数据不足不是错误？

这是解码层与 .NET `BinaryReader` 最本质的分歧。`BinaryReader.ReadInt32()` 在只剩 2 字节时直接抛 `EndOfStreamException`
——它假设调用者已确保数据完整。

但现实是： **在网络编程中，你不知道数据是否完整**。TCP 一次性给你 250 字节，但消息体声明了 500
字节长度。解码器不能因为自己读不到就崩溃——数据在路上，只是还没到。

Sonic 的解码器采用 `out bytesConsumed` 约定：

- `bytesConsumed > 0`：成功解码，缓冲区前进 `bytesConsumed`。
- `bytesConsumed == 0`：数据不足，等待更多数据。 **不抛异常**。
- 格式非法（VarInt 超过 10 字节、非法 UTF-8）：这才是异常。

流控和错误被彻底分离。调用方不需要 `try-catch` 做流控。

## 为什么解码器无状态？

与编码层对称：解码规则是确定性的。给定一段字节 `[0x00, 0x00, 0x00, 0x2A]`，大端解码永远是 `42`
。不需要跨调用的状态。每次调用消费一段字节，返回值和消耗量，调用方负责切片 `buffer = buffer.Slice(bytesConsumed)`。

**缓冲区管理不是解码器的职责**。解码器只做规则转换，缓冲区的前进和重用由上层（反序列化器、还原器）控制。

## 为什么选择 `out` 而非 `Result<T, Error>`？

两个原因：

1. **热路径性能**：解码基本类型是每帧最低层的操作，一个 MessagePack 帧可能有上千次 `decode_i32`。`out int` + 返回值是 JIT
   最激进的内联优化目标，零分配。`Result<T>` 无论值类型怎么优化，都有额外的分支和可能的分配。

2. **数据不足不是函数式意义上的 "Error"**：`Result` 的 Err 分支表示"操作失败"，但数据不足是"再试一次"，语义完全不同。用
   `bytesConsumed == 0` 表达"数据不足，再来点"，与 `Result` 的 Err 语义不冲突且更高效。

## 不应该承担什么职责？

- **不应管理读取缓冲区**：解码器接受 `ReadOnlySpan<byte>` 切片，由调用者管理缓冲区生命周期。
- **不应做 I/O**：解码器不主动发起 `ReadAsync`。等待更多数据是调用者的循环逻辑。
- **不应解析帧边界**：解码器不知道也不关心里面的长度前缀是哪来的。如果给它 10 字节让它 decode 一个声称 5
  字节就能读完的类型，剩余字节是调用者需要关心的。
- **不应处理字符编码**：与编码层对称，解码器返回 `Utf8Text`（已验证 UTF-8），调用者自行决定何时 `ToString()`。

## 与上下游的衔接

```
上游（缓冲区 / Unframe 输出的帧载荷）→ ReadOnlySpan<byte>
    ↓
IDecoder.decode_i32(buffer, out consumed) → 解码值 + 消耗字节数
    ↓
下游（反序列化器 / 还原器）→ 切片 buffer = buffer.Slice(consumed)，继续解析
```

## 典型场景

- **二进制协议解析**：帧载荷是一段二进制 blob，解码器逐字段读取 `i32`、`i64`、`f32`。
- **多轮协商**：先读 1 字节协议版本号，根据版本号切换不同解码策略。
- **零拷贝字符串**：`decode_utf8` 返回的 `Utf8Text` 直接指向原始帧载荷，在不需要长期持有的场景（日志解析、消息路由）完全避免字符串分配。
