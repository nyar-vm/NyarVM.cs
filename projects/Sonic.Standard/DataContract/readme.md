# DataContract — 数据契约与验证

## 定位

DataContract 是 Sonic.Data 三维架构中负责"数据应该是什么"的维度。它与 DataProcess（数据如何流动）和
DataStorage（数据如何落地）正交。DataContract 不参与字节转换，只对内存中的对象进行"质检验收"。

## 为什么验证要独立于序列化？

这是最容易犯的设计错误：在序列化器里加 `[Required]` 验证，在反序列化时一并检查。

问题在于 **验证的时机和错误模型与序列化完全不同**：

1. **验证发生在反序列化之后**。反序列化成功才能拿到完整对象，才能做跨字段验证（"如果 `Country` 是 US，则 `State` 必填"
   ）。把验证嵌入反序列化流程，等于要求反序列化器理解业务规则——这会破坏其格式无关性。

2. **验证需要收集全部错误，序列化是快速失败**。用户提交表单，你希望一次返回所有验证错误（"姓名必填"+"年龄超出范围"+"
   邮箱格式非法"），而不是修一个报一个。但序列化遇到格式破坏（非法 UTF-8、截断的帧）应立即停止——继续解析只会产生海量虚假错误。两种错误模型互斥。

3. **验证规则有层级依赖**。`StringLength(min: 1, max: 50)` 需要完整的字符串对象才能检查；`RequiredWhen("Country", "US")`
   需要另一个字段的值。反序列化器在逐字段消费字节流时，根本不可能做跨字段验证——引用的字段还没读到。

因此 DataContract 的验证器接口设计为： **接受已构造的完整对象 T，返回 `ValidationResult`（错误列表）**。它在管道中位于反序列化之后、业务逻辑之前。

## 为什么不是 Attribute-Driven 就够了？

`[Required]`、`[StringLength]`、`[Range]` 这些声明式属性覆盖了 80% 的场景。但剩余 20% 需要复杂逻辑：

- "开始日期必须早于结束日期"
- "如果订单金额 > 10000，则需要审批人"
- "用户名不能与已有用户重复"（需要查数据库）

纯属性无法表达这些。DataContract 提供 `IValidator<T>` 接口，源生成器从属性自动生成基础验证，同时允许手动添加
`[CustomValidation]` 方法，两者合并产生最终验证结果。

## 为什么 `Schema<T>` 是可选生成的？

`Schema<T>` 提供字段名、类型、验证规则的运行时元数据，用于：动态表单生成、API 文档自动生成、数据库迁移脚本生成。

但它不是免费的——每个带 `[Data]` 的类型都生成 `Schema<T>` 会显著增加编译产物。因此 `generate_meta` 默认为 `true`
（大多数场景需要），但可以在不需要元数据的纯内部 DTO 上显式关闭。

## 不应该承担什么职责？

- **不应参与字节转换**：DataContract 的验证器接受对象 T，返回验证结果。它不知道也不应该知道 T 是从 JSON、MessagePack
  还是投射路径来的。
- **不应用异常表达验证失败**：验证失败不是程序错误，是用户输入不合法。异常意味着"程序出了意外"，而"邮箱格式不对"是预期内的业务状态。用
  `ValidationResult` 返回，调用方自行决定是返回 422 给前端还是记录日志。
- **不应替代类型系统**：能用 `uint` 表达"非负"就不要用 `[Range(min: 0)]`。类型系统在编译期保证, DataContract 在运行期补充。
- **不应硬编码错误消息**：`error_message` 参数允许自定义，但默认走资源文件（国际化）。汉语服务不应返回英文错误消息。

## 与上下游的衔接

```
上游（DataProcess 反序列化）→ 内存中的对象 T
    ↓
IValidator<T>.validate(target) → ValidationResult { errors: [...], warnings: [...] }
    ↓
下游（业务逻辑 / HTTP 响应）→ if (!result.is_valid()) return 422(result.errors)
```

## 典型场景

- **Web API 请求校验**：`[Data]` DTO 自动生成 `Validator<CreateOrderRequest>`。Controller 中一行
  `var result = validator.validate(request)` 完成校验，错误直接序列化为 JSON 返回。
- **配置文件启动检查**：`appsettings.json` 反序列化为 `AppConfig` 后，验证器检查所有配置项的合法性，失败则拒绝启动并打印所有错误。
- **消息队列消费**：消费端从 Kafka 收到消息，反序列化后先验证再处理。无效消息进入死信队列（DLQ），不是直接崩溃。
