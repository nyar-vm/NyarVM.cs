## 摘要

当代编译器与语言工具链深陷“人肉驱动”的泥潭。从 LLVM 的海量手工维护，到 MLIR
的“语法优先”歧途，整个领域缺乏一套基于第一性原理的统一理论。编程语言理论（PLT）在数十年痛苦探索后，揭示了三个根本性的原理：对象代数（Object
Algebras）解决了表示与扩展的二元性，等式饱和（Equality Saturation）提供了无相位排序的优化范式，部分求值及其 Futamura
投影（Partial Evaluation）则实现了语义驱动的自动编译器生成。本文提出 Nyar 元编译器框架，首次将三大第一性原理融为一个内聚的代数体系。Nyar
以对象代数替代传统 IR，以等式饱和替代线性 Pass 管道，以部分求值替代手工 Lowering。我们证明，这一范式不仅从根本上终结了表达式问题（Expression
Problem），更将编译器的设计从“经验堆砌”升华为“理论推导”，从而使得任何程序语言特性的添加和任何程序分析/优化的实现都能独立扩展且自动互操作。Nyar
不是对 LLVM/MLIR 的渐进改良，而是编译器基础设施的赛道切换。本文给出其完整的形式化描述、架构设计和工程落地路径，论证 Nyar
是未来编译界唯一的必然答案。

> **关键词：** 对象代数，等式饱和，Futamura 投影，表达式问题，元编译器，方言系统，第一性原理

## 第一章 引言：编译器界的永恒困境与第一性原理的缺失

### 1.1 一个幻象笼罩的领域

自 Grace Hopper 发明第一个编译器以来，编译技术始终在“表达力”与“可扩展性”之间痛苦摇摆。面向对象编程通过类继承轻松添加新数据类型，却难以添加新操作；函数式编程通过模式匹配自然添加新操作，却难以添加新数据类型。这就是著名的
**表达式问题（Expression Problem）**，由 Philip Wadler 在 1998
年正式命名。编译器作为程序语言特性的集合（数据类型）与优化/分析/代码生成等操作（操作）的集中体现，承受着这一问题的最猛烈冲击。

七十年来，无数架构试图回应这一困境，却无一不在第一性原理面前折戟沉沙。UNCOL（Universal Computer Oriented
Language）试图成为通用中间语言而失败；GCC 的 RTL 固化成了一堆难以扩展的宏；LLVM IR 在十数年间膨胀为一座“屎山”；MLIR
带着“多级方言”的承诺高调登场，却迅速沦为“方言爆炸”的集中营。每一个新范式都宣称自己是终极答案，但最终都暴露出相同的内伤：
**它们都是基于工程直觉的“启发式架构”，而非基于严格原理的“推导式系统”。**

### 1.2 错误地基上的宏大叙事

今天主流的编译器基础设施——LLVM 与 MLIR——可以被看作一个巨大的社会契约：开发者同意维护海量的手工代码，以换取一定程度的可重用性。这个契约建立在三个隐含的前提之上：

1. 程序的中间表示（IR）必须是某种具体的数据结构（如 SSA 图或操作-值图）。
2. 优化必须被组织成一个顺序的、破坏性的 Pass 管道。
3. 不同抽象层次的语言（方言）之间的转换必须由人工编写的 Lowering 规则执行。

这三个前提没有任何理论上的必然性，它们只是历史惯性。更致命的是，它们直接与编程语言理论已经发现的第一性原理相矛盾。因此，整个现代编译器大厦是建立在错误地基上的。这个地基正在不可避免地走向崩塌：LLVM
的维护成本已经高到被其首席维护者称为“不可持续”；MLIR 则被批评患上了“MLIR 病（MLIR
Disease）”——幻想一个元框架能解决所有问题，实际却把复杂性推给了方言作者。

### 1.3 编译器设计的真正问题是什么？

让我们剥离所有工程细节，直指编译器设计的本源。一个编译器或语言工具链需要处理三个正交的维度：

- **构造维度（Constructs）**：语言提供了哪些语法和语义构造？例如整数、加法、函数、闭包、模式匹配。
- **操作维度（Operations）**：对这些程序执行哪些处理？例如类型检查、优化、代码生成、格式化、文档生成。
- **转换维度（Transformations）**：如何在不同的抽象表示（方言）之间保持语义等价的映射？例如从张量运算降低到向量化的循环。

传统架构将构造固化为数据结构（AST 节点 / IR 指令），将操作表达为遍历这些结构的函数（Visitor /
Pass），将转换硬编码为手工翻译函数。这使得任何一个维度的扩展都需要侵入其他两个维度。表达式问题揭示了这种固化的根本缺陷：它不可能同时实现构造和操作的独立扩展。

### 1.4 第一性原理的浮现

编程语言理论在数十年对“可扩展语言”的探索中，逐渐识别出三个根本的、不可再分的原理。它们分别对应上述三个维度：

| 维度     | 传统解决方案     | 第一性原理                                        |
|----------|------------------|---------------------------------------------------|
| 构造维度 | 具体 IR 数据结构 | **对象代数 (Object Algebras)**                    |
| 操作维度 | 线性 Pass 管道   | **等式饱和 (Equality Saturation)**                |
| 转换维度 | 手工 Lowering    | **部分求值 / Futamura 投影 (Partial Evaluation)** |

这三个原理各自具有深刻的数学基础：对象代数源自范畴论中的 F-algebra 和 Church 编码；等式饱和源自抽象重写系统和等价类理论；Futamura
投影源自计算模型的语义特化。更重要的是，它们之间存在天然的协同效应：对象代数提供的多态表示可以直接注入到等式饱和的 EGraph
中，而等式饱和的等价探索又为部分求值提供了完美的残留表达环境。三者合一，构成了一个逻辑自洽、完备无缺的元编译器理论核心。

### 1.5 Nyar：三位一体的必然答案

Nyar 正是基于这三大第一性原理构建的元编译器框架。“元编译器”意味着它不直接生成一个具体的编译器，而是生成生成编译器的框架——它是一个编译器生成器生成器。Nyar
的用户只需用抽象代数的方式定义自己语言的方言，框架便自动派生出：

- 等价的 AST 和 PSI 节点（当需要具体语法树时）
- EGraph 构造器，将程序直接表达为等价类图
- 部分求值构造器，自动从解释器推导出编译器
- 类型检查、代码格式化、文档生成、测试生成等一切可定义的“操作”

所有的派生都遵从对象代数，因此用户的原始定义——一个方言接口——便成为了单一事实来源。新增一个语言构造，只需在接口中添加一个方法签名；新增一个程序操作，只需提供一个该接口的新实现。一切都无需修改已有代码。表达式问题被彻底终结。

Nyar 不是对 LLVM 或 MLIR 的改良，而是对整个范式的替换。本白皮书将详细阐述这一替换的学理依据、形式化基础、工程路径和未来愿景。

## 第二章 错误地基：对主流编译器架构的批判

在建立 Nyar 的正向理论之前，必须对现有的错误地基进行彻底的解剖。唯有理解它们为何失败，才能理解第一性原理何以必然。

### 2.1 LLVM：人肉驱动的“巴别塔”

LLVM（Low Level Virtual Machine）自 2000 年启动以来，已成长为事实上的工业级编译器基础设施。它提供一种强类型的 SSA 中间表示（LLVM
IR），以及一个庞大的优化 Pass 库。然而，其辉煌外表之下隐藏着结构性的不可持续性。

**2.1.1 IR 语义的模糊性与未定义行为的泥潭**

LLVM IR 的核心缺陷是缺乏一个形式化的操作语义。其语义文档由英文散文构成，充满了未定义的角落。例如，`getelementptr`
指令的行为在各种边界情形下依赖于开发者的“共识”而非严格规范。这直接导致了一个悖论：编译器的正确性依赖于优化 Pass
的正确性，但优化的合法性又依赖于 IR 的语义——由于语义未定义，无人能确切知道一个优化是否合法。LLVM 大量使用 **未定义行为（Undefined
Behavior, UB）** 作为优化机会的来源，但 UB 本身却成为了 bug 和不安全性的温床。一个底层系统如果连自己 IR
的含义都无法精确说明，便已经违背了编译器作为“语义保持转换器”的根本定义。

**2.1.2 线性 Pass 管道的相位排序灾难**

LLVM 的优化系统由数百个 Pass 组成，它们按预定顺序一个接一个地执行。Pass A 的输出是 Pass B 的输入，且 A 的决策无法被 B
之后的信息回溯修正。这种线性架构导致了著名的 **相位排序问题（Phase Ordering Problem）**
：一个优化可能破坏另一个优化的前置条件，或者两个优化的最佳顺序因程序特征而异。LLVM 社区只能通过反复试验固定一个“还凑合”的
Pass 顺序，然后为特定的 benchmark 反复微调。这本质上是用穷举弥补理论的缺失。每一次新增一个
Pass，都可能需要在全局管道中重新寻找最佳位置，这从根本上断绝了 Pass 的可组合性。

**2.1.3 维护的不可持续性与审查瓶颈**

LLVM 项目的主要维护者多次公开表示，其增长速度已经超过了审查能力（Review
Capacity）。贡献者众多，但能理解全局影响并作出负责任审查的人极少。这导致代码质量下降、技术债务堆积。更重要的是，LLVM
极度排斥架构性革新，因为任何对 IR 或 Pass
管理器的微小改变都会牵连成百上千个下游项目。整个系统陷入了“复杂性锁定”——项目太庞大以至于无法进行根本性重构，只能在旧框架上不断打补丁。这正是“人肉驱动”的终极形态。

### 2.2 MLIR：在错误的路上越走越远

MLIR（Multi-Level Intermediate Representation）诞生于 LLVM 生态内部，意图解决 LLVM IR
过于底层、领域特定抽象难以表达的问题。它引入了“方言（Dialect）”的概念，允许用户定义自己的操作、类型和 IR 结构。然而，MLIR
的设计哲学从根本上就是错误的，它只是把 LLVM 的问题“升级”到了一个更复杂、更分散的层面。

**2.2.1 语法优先，语义缺失：MLIR 病的根源**

MLIR 的核心理念是“定义你的方言语法”。它提供了 Operation、Value、Type、Attribute 等基础组件，并允许通过 TableGen 自定义操作。然而，MLIR
几乎完全把操作的 **语义**留给了用户。框架本身不关心也不验证语义：它不知道 `arith.addi` 和 `tensor.matmul` 之间是否存在等价关系，不保证一个
Lowering 转换确实保持了语义，也不提供任何机制来自动检查方言组合的正确性。这是一种彻底的“语法优先（Syntax-First）”范式。社区将由此导致的后果称为
**“MLIR 病（MLIR Disease）”**：以为只要能用语法定义无数方言，所有编译问题就自然解决了。实际上，真正的困难——优化、转换的正确性、组合性——全部被转嫁给了方言作者。

**2.2.2 方言爆炸与组合性的虚假承诺**

MLIR 鼓励项目定义自己的方言，导致了一个碎片化的生态系统。不同团队甚至同一公司内的不同项目使用的方言互不兼容。MLIR
声称方言可以自由组合，但在实践中，将 `linalg` 方言与 `scf`
方言混合可能会产生类型不匹配、非法操作等难以调试的错误。因为缺乏对语义组合的形式化约束，跨方言优化几乎不可能自动进行。每个方言的作者都必须手写针对其他方言的
ConversionPattern，工作量和错误率随方言数量平方增长。MLIR 没有解决组合性问题，只是提供了一个发生组合性灾难的更大舞台。

**2.2.3 手写 Lowering 的线性本质未变**

MLIR 的 Lowering 仍然是通过手工编写模式匹配规则实现的。这与 LLVM 的 Lowering 没有本质区别，只是换了一个环境。相位排序问题依然存在：不同
Lowering 和优化 Pass 之间仍然需要手工编排顺序。而且由于方言可以任意定义，全局的 Pass 管道变得更加不可能设计和维护。MLIR
所提供的灵活性，实际转化为复杂性，并把复杂性抛向用户。它的缔造者后来也反思，业界曾“误以为”MLIR
能像魔法一样把众多小方言组合成有用的东西，但实际上它距离这个目标还很远。

### 2.3 GraalVM：对了一半的愿景

GraalVM 的 Truffle 框架提供了一种语言实现框架：语言作者只需编写一个树形解释器，Truffle 的编译器便会自动通过部分求值和编译技术生成高效的机器码。这暗合了
Futamura 投影的思想，因此我们说它“对了一半”。然而，GraalVM 存在根本性的局限：

- **封闭的生态与 Java 绑定**：它深深耦合于 JVM 生态系统，无法作为通用的、独立于语言的元编译器框架。
- **解释器编写负担**：Truffle 要求语言作者用 Java 编写 AST 解释器，这又回到了手工定义 AST 节点类的老路，没有解决表达式问题。
- **特化黑盒**：Graal 的特化过程是一个复杂的黑盒，用户难以控制和理解其中间表示，也难以将自己的领域优化知识注入。

GraalVM 验证了部分求值作为语言实现基础的可行性，但它没有意识到对象代数和等式饱和的必要性，因此它无法成为一个真正可无限扩展的元编译器。

### 2.4 共同的根本缺陷：第一性原理的集体缺失

所有上述架构共享同一个原罪： **它们不是从第一性原理推导出来的，而是工程直觉的堆积。**

编译器领域的第一性原理应该告诉我们：

1. **程序的表示如何与程序的内容解耦？** 传统 IR 将表示固化为数据结构，导致了构造的不可扩展。理论早已给出答案：程序是一个接受抽象工厂的多态函数（对象代数）。
2. **程序的优化如何避免定序？** 传统 Pass 管道强制序列化，导致了相位排序问题。理论早已给出答案：优化是对程序空间的等价饱和探索（等式饱和）。
3. **程序的转换如何从语义自动推导？** 传统 Lowering 手工翻译，导致了维护灾难。理论早已给出答案：编译器是解释器的特化（Futamura
   投影）。

主流的编译器界无视这些理论成果，继续在错误的地基上堆砌砖瓦。Nyar 的出现，就是要结束这场持续七十年的“经验主义狂欢”，将编译器设计带回到以原理为中心的轨道上。

## 第三章 第一性原理：PLT 的三大发现

编程语言理论经过数十年对类型系统、重写系统和部分计算的研究，分别收敛到了三个根本性的原理。它们各自独立地解决了编译器中一个维度的问题，但它们的融合才构成真正的革命。

### 3.1 对象代数：表达性与可扩展性的统一

对象代数（Object Algebras）由 Bruno C. d. S. Oliveira 等人在 2012 年左右系统化，但其思想可追溯到 Church 编码、F-algebra 和
Tagless Final 风格。其核心洞察是： **语言构造不应定义为具体的数据类型，而应定义为一个抽象工厂接口的方法**。

#### 3.1.1 从 Church 编码到 F-Algebra

在范畴论中，一个递归数据类型（如表达式 AST）可以通过其基函子 $F$ 的初始代数（initial F-algebra）来刻画。例如，一个简单算术语言的基函子为：

$$
F (X) = \mathbb{Z} \uplus X \times X \uplus X \times X
$$

分别对应常量、加法和乘法。初始代数 $(\mu F, in)$ 给出了这个语言的 AST。然而，初始代数是“最终的”表示：一旦固定，所有操作都必须通过
catamorphism（fold）来定义，这导致添加新构造极其困难。

对象代数则采用 **最终代数**的视角：将语言定义为对所有可能解释的接口。对于一个语言 $\mathcal{L}$
，我们定义一个代数接口 $Alg_{\mathcal{L}}$，它为一个载体类型 $E$ 提供每个构造的解释：

$$
\begin{aligned} &lit : \mathbb{Z} \to E \\ &add : E \times E \to E \\ &mul : E \times E \to E \end{aligned}
$$

一个程序 $p$ 不再是具体的 AST，而是一个多态函数 $\Lambda E. \, (Alg_{\mathcal{L}} (E)) \to E$
，即给定任何实现了该接口的工厂，程序调用其方法构造出期望的效果。这正是 Church 编码的本质，只是被提升到了接口层面。

#### 3.1.2 双向可扩展性与表达式问题的终结

因为程序被抽象成了多态函数，我们可以为同一个接口提供无限多种实现：

- 令 $E = int$，则得到求值器。
- 令 $E = string$，则得到美化打印器。
- 令 $E = IType$，则得到类型检查器。
- 令 $E = Id$（EGraph 的 e-class ID），则得到优化图构造器。

这些实现都是 **操作维度**的扩展，无需修改程序定义。

当需要增加新的语言构造（如减法、变量绑定）时，我们通过 **接口继承**定义扩展代数 $Alg_{\mathcal{L}'} (E)$
，它继承 $Alg_{\mathcal{L}} (E)$ 并添加新方法。旧程序（只使用旧构造）无需修改即可接受扩展后的工厂。新的工厂可以选择升级以支持新构造。这便同时实现了
**构造维度的扩展**。

对象代数因此成为第一个在严格静态类型系统中同时解决两个扩展维度的方案。它将表达式问题化为类型系统的多态与继承问题，完成了从“数据导向”到“行为导向”的范式转换。

#### 3.1.3 高阶抽象语法（HOAS）

传统 AST 在处理变量绑定时需要 De Bruijn 索引或唯一名字，极易出错。对象代数可以利用宿主语言的闭包来直接表达作用域：

```text
Let(string name, E rhs, E -> E body)
```

其中 `body` 是一个将变量绑定所对应的 `E` 转换为整个作用域 `E`
的函数。宿主语言的词法作用域自动保证了变量不会逃逸或冲突。这种高阶抽象语法（HOAS）使得绑定的语义被宿主语言编译器检查，消除了整个错误类别。

### 3.2 等式饱和：优化即等价探索

等式饱和（Equality Saturation）是近年来由 Willsey 等人发展的优化技术，其基础是抽象重写系统与等价类图。

#### 3.2.1 抽象重写系统与相位排序问题

传统优化器以破坏性方式重写
IR：当应用一个优化规则时，原始表达式被替换，旧信息丢失。这导致优化顺序至关重要，并且优化器无法回溯。抽象重写系统理论指出，重写的正确性应当通过选择等价类中一个合适代表来保证，而不是通过强制进行特定的重写序列。

#### 3.2.2 EGraph：表达式的等价类

EGraph 是一种高效数据结构，用于紧凑表示大量等价表达式。它将每个表达式节点映射到等价类（e-class），并维持节点间的等价关系。EGraph
支持两种关键操作：

- **添加（Add）**：将一个表达式插入 EGraph，若已存在则返回其 e-class ID。
- **合并（Merge）**：将两个 e-class 合并为一个，触发所有包含它们作为子节点的父节点的重新哈希和可能进一步的合并（同余闭包）。

通过这两个操作，我们可以不断应用重写规则 `lhs -> rhs`，每次将 `lhs` 和 `rhs` 的 e-class 合并，而 **不丢弃任何信息**。这个过程称为
**饱和（Saturation）**，直到不能再合并为止。最终 EGraph 包含了程序在所有应用规则下的等价闭包。

#### 3.2.3 无相位的全局优化

由于所有规则都可以任意顺序应用，且等价关系是累积的，EGraph 完全消除了相位排序问题。优化不再是线性序列，而是一种 **饱和计算**
：给定一个初始程序和一个规则集，计算其等价闭包，然后通过一个成本模型从每个 e-class
中提取最优表达式。这个范式将优化从“如何优化”转变为“声明什么是等价的”，从而将优化器的正确性完全依赖于规则的局部正确性。这极大地降低了设计复杂性和潜在
bug。

### 3.3 部分求值与 Futamura 投影：自动编译器生成

部分求值（Partial Evaluation）是一种将程序与其部分输入特化以生成高效残余程序的技术。设有一个程序 $p$，接受静态输入 $s$
和动态输入 $d$。一个部分求值器 $\text{PE}$ 满足：

$$
\text{PE} (p, s) \equiv \lambda d. \, p (s, d)
$$

也就是说，$\text{PE} (p, s)$ 是一个新的程序，它等待剩余的动态输入 $d$，然后产生与 $p (s, d)$ 相同的结果。但因为在特化时 $s$
是已知的，可以大量进行常量化简、展开和内联，从而提高效率。

#### 3.3.1 Futamura 投影：从解释器到编译器

Futamura 在 1971 年发现了三个深远的投影：

- **第一投影**：将解释器 $int$ 与源程序 $source$ 特化：
  $$ \text{PE} (int, source) \equiv target $$
  得到一个目标程序 $target$，它不需要解释器就能直接执行源程序的功能。这其实就是 **编译**。因此，编译器可以从解释器
  **自动生成**。

- **第二投影**：将部分求值器自身与解释器特化：
  $$ \text{PE} (\text{PE}, int) \equiv compiler $$
  得到一个编译器生成器：给一个解释器，返回该语言的编译器。

- **第三投影**：将部分求值器与自身特化：
  $$ \text{PE} (\text{PE}, \text{PE}) \equiv compiler\_generator $$
  得到一个编译器生成器生成器，即可以自动生成针对任意解释器的编译器生成器。

这三个投影证明： **Lowering 不是必须要手写的。** 如果你拥有语言的操作语义（即一个解释器），那么编译器（以及它的生成器）是可以机械地从部分求值器推导出来的。传统
Lowering 手工翻译，完全可以用对解释器的部分求值来取代。

### 3.4 三大原理的互补与必然融合

独立地看，每个原理都有局限：

- 对象代数解决了构造和操作的扩展问题，但没有解决如何声明等价优化（Pass 的扩展）以及不同代数之间的自动转换。
- 等式饱和解决了优化声明和相位排序，但假设表达式类型是固定的（固定的节点类型），无法自动适应新的语言构造。
- 部分求值解决了自动推导编译器，但残留表达式仍需要优化，且难以处理高阶控制流。

然而，当它们被融合在一个统一框架内时，便形成了完美的互补：

- 对象代数提供可扩展的构造定义，程序作为代数上的多态函数。
- 该多态函数可以直接由等式饱和的 EGraph Builder 解释，将程序表示为 EGgraph 中的等价类，从而获得无相位的优化能力。
- 同时，部分求值 PE Builder 利用相同的代数接口对程序进行特化，自动推导方言转换（Lowering）而不需要手工编写规则。

它们共享同一个代数接口，因此任何语言方言的定义都可以自动在所有三种“模式”（求值、优化、特化）下工作。这就是 Nyar 三位一体架构的必然性。

## 第四章 Nyar 范式：三位一体的元编译器理论

Nyar 的架构可以简化为三个等式，代表着对传统范式的彻底替换：

- **OA 替代 IR**：语言构造定义为对象代数接口，程序是多态函数。
- **EGraph 替代 Pass**：优化器是对程序空间的等式饱和探索。
- **PE 替代 Lowering**：方言转换是解释器的部分求值。

本节详细阐述这一范式如何运作。

### 4.1 OA 替代 IR：程序作为多态构造

在 Nyar 中，不存在传统意义上的全局 IR（如 LLVM IR 或 MLIR Operation）。取而代之的是，每一种“语言”或“方言”被定义为一个参数化的代数接口。例如，Core
方言：

$$
\begin{aligned} \mathtt{ICoreAlg}[E] = \{ \\ &\mathtt{lit} : \mathbb{Z} \to E, \\ &\mathtt{add} : E \times E \to E, \\ &\mathtt{alloc} : \mathbb{N} \to E, \\ &\mathtt{load} : E \to E, \\ &\mathtt{store} : E \times E \to E, \\ &\dots \} \end{aligned}
$$

一个程序（比如一个函数）的类型为 $\forall E. \, \mathtt{ICoreAlg}[E] \Rightarrow \dots \Rightarrow E$
。这意味着程序可以操作任何支持这些操作的表示 `E`。

这个简单的改变带来革命性的后果：

1. **表示的独立性**：我们不再需要构造具体 AST。程序就是一段泛型代码，在不同上下文中被实例化。对于需要具体语法树（例如 IDE 的
   PSI）的场景，我们提供 `E = PsiNode` 的工厂实现，生成具象节点。对于不需要的场景（如直接解释执行），`E = Value`，不产生任何中间树。
2. **操作的可扩展性**：增加一个新的分析或优化，就是提供一个新的工厂实现 `ICoreAlg[AnalysisResult]`。这完全独立于语言定义，且可以被任意方言复用。
3. **构造的可扩展性**：添加新操作通过接口继承 `IExtAlg[E] : ICoreAlg[E]` 实现，已有的工厂可以选择性升级。旧程序无需知晓新操作。

### 4.2 EGraph 替代 Pass：饱和式优化网络

在 Nyar 中，优化不再由顺序执行的 Pass 构成，而是通过一个特殊的工厂实现： **EGraph Builder**。我们将 `E` 绑定为 `Id`（EGraph 的
e-class 标识符），并提供 `ICoreAlg[Id]` 的实现：

- 每次调用 `add(Id a, Id b)` 时，Builder 在 EGraph 中创建或查找一个 `Add` 节点，其子节点为 `a` 和 `b` 对应的
  e-class，并返回这个节点的 e-class ID。

重写规则被声明为等价关系，而不是转换函数。例如：

$$
\mathtt{add} (\mathtt{lit} (a), \mathtt{lit} (b)) \equiv \mathtt{lit} (a+b)
$$

这条规则告诉 EGraph 引擎，将匹配到的模式两端合并。规则可以无限应用，直到饱和。整个程序的等价闭包被构建出来。

成本模型（Cost Model）然后从每个 e-class 中选择一个实现成本最低的节点，作为最终的“优化后程序”输出。这种方法：

- **消除相位排序**：因为规则是无序的、声明式的，优化器不依赖于应用顺序。
- **自然跨方言**：如果一个程序混合使用了 Core 方言和 Tensor 方言，我们只需要提供一个实现了 `ICoreAlg` 和 `ITensorAlg` 的组合
  EGraph Builder，所有跨方言的规则都可以在同一 EGraph 中匹配和合并。这实现了真正的跨方言联合优化。

### 4.3 PE 替代 Lowering：语义驱动的方言转换

方言之间的转换（如 Tensor → Core）在传统方法中通过手写 Lowering 规则实现。Nyar 采用 Futamura 投影：如果我们有一个 Tensor
解释器，它实现了 `ITensorAlg[Value]`，将 Tensor 操作解释为对具体值的计算，那么我们可以将这个解释器与一个部分求值器组合。

Nyar 的部分求值器通过 `PEBuilder` 工厂实现，它将 `E` 绑定为 $(Static, Value, Residual)$ 三元组。给定一个 Tensor 程序（一段使用
`ITensorAlg` 的多态函数），PEBuilder 会：

1. 将静态已知的部分直接计算（通过调用解释器的方法）。
2. 将动态未知的部分残留为新的表达式（使用 Core 方言的构造）。

结果是一个新的程序，其类型变为 $\forall E. \, \mathtt{ICoreAlg}[E] \Rightarrow \dots \Rightarrow E$。这个过程 **自动推导**
出了从 Tensor 到 Core 的编译器。我们不再需要手写 Lowering 规则，只需要提供 Tensor 的解释器即可。这不仅极大地减少了工作量，而且保证了
Lowering 的语义正确性（因为它是从解释器语义推导出来的）。

### 4.4 整合架构：方言网络与 EGraph 共存

Nyar 将上述三部分整合为一个 **方言网络**。任何方言都可能作为其他方言的源或目标。方言之间不强制经过一个“中央
IR”，而是构成一个图。优化器（EGraph）在这个图上操作：它可以同时展开 Tensor 表达式的等价类，以及其 Lowering 到 Core
的等价类，并让成本模型自动选择最佳路径。

这个架构的优雅之处在于，它完全由一套对象代数接口所驱动。定义一个方言就是定义一个代数接口；实现几个标准工厂（EGraph
Builder、PE Builder、IKun Bridge 等）就自动获得了优化和 Lowering 能力。这一切都是通过元生成器（Source
Generator）自动化完成的，用户只需关注语言语义的核心。

### 4.5 Expression Problem 的终极解答

综合来看，Nyar 彻底解决了表达式问题：

- **添加新语言构造**：定义一个新的代数接口继承已有接口。已有的程序（仅使用旧接口）不受任何影响。需要处理新构造的分析/优化可以通过实现新接口并继承旧工厂来扩展，或在新的工厂中实现。
- **添加新操作（Pass/分析）**：为方言接口提供一个新实现。所有用该方言编写的程序自动适用于新操作，无需修改程序代码。

在 Nyar 中，语言构造和程序操作不仅是可独立扩展的，而且是通过静态类型系统安全组合的。这是编译器架构领域的“圣杯”，Nyar
首次在工业级平台上完全兑现了这一承诺。

## 第五章 形式化基础与核心定理

为赋予 Nyar 坚实的理论基础，本节使用严格的数学语言和 LaTeX 形式化其核心构造。我们假设读者熟悉基本范畴论和类型理论。

### 5.1 对象代数的范畴模型

设语言方言 $\mathcal{L}$ 由一组操作符 $\Sigma$ 签名给出，每个操作符具有元数 $(n, m)$ 及可能的类型依赖。$\mathcal{L}$
的一个解释（代数）由载体对象 $E$ 和解释映射给出。在范畴论中，这对应于 **F-algebra**
。具体地，定义语法域函子 $F_{\mathcal{L}} : \mathbf{Set} \to \mathbf{Set}$ 为：

$$
F_{\mathcal{L}} (X) = \bigoplus_{op \in \Sigma} X^{arity (op)}
$$

则初始 F-algebra $(\mu F_{\mathcal{L}}, in)$ 构成该语言的初始代数（即 AST）。对象代数采用 **最终代数**
视角，但不固定载体。定义 $\mathcal{L}$ 的代数接口为所有形如 $F_{\mathcal{L}} (X) \to X$ 的箭头（在泛化代数中，$X$
可被参数化）。一个程序 $p$ 是自然变换：

$$
p : \forall X. \, (F_{\mathcal{L}} (X) \to X) \implies X
$$

即它在任何代数上多态地计算出一个结果。这个类型正是 Church 编码在 System F 中的表述，保证了表示独立性。

**定理 1（表达力）**：对于任意以初始代数给出的递归程序，存在一个同构的对象代数表示，且此表示保留了所有代数结构。

### 5.2 EGraph 的代数语义

EGraph 可以看作一个 **等价闭包算子**。设程序 $p$ 在 EGgraph Builder
下的解释为 $\llbracket p \rrbracket_{EG} \in \mathbf{EGraph}$，其中 EGgraph 是 e-class 图。重写规则集合 $\mathcal{R}$ 定义了
EGraph 上的合并关系。饱和过程计算最小不动点：

$$
\mathcal{E}^* = \text{Saturate}_{\mathcal{R}} (\llbracket p \rrbracket_{EG})
$$

**定理 2（无相位优化）**：对于任意规则集 $\mathcal{R}$ 和初始程序 $p$，饱和 EGraph $\mathcal{E}^*$ 中的所有 e-class
包含相同的语义值（假设规则语义保持）。因此，任何通过成本模型从 $\mathcal{E}^*$ 提取的表达式都与原始程序 $p$
语义等价。提取结果不依赖于规则应用顺序。

证明大意：等价合并操作是可交换和可结合的，且同余闭包保证了传递性。因此，饱和过程是一个可交换的收敛过程，无关于顺序。

### 5.3 部分求值与 Futamura 投影的类型化表述

设部分求值器类型为：

$$
PE : \forall A, B, C. \, (A \times B \to C) \times A \to (B \to C)
$$

其中 $A$ 是静态输入类型，$B$ 是动态输入类型。给定语言 $\mathcal{L}$
的解释器 $int : \mathcal{L}\text{-}Prog \times Input \to Output$，以及一个部分求值器 $pe$，第一 Futamura 投影为：

$$
compile = \lambda prog. \, pe (int, prog)
$$

其类型为 $\mathcal{L}\text{-}Prog \to (Input \to Output)$，这就是编译器。

**定理 3（自动 Lowering）**：设上层方言 $\mathcal{L}_H$ 有解释器 $int_H$，其目标域为下层方言 $\mathcal{L}_L$
的值域，则对 $int_H$ 应用部分求值即可得到将 $\mathcal{L}_H$ 程序特化为 $\mathcal{L}_L$ 程序的转换器。这保证语义保持性。

Nyar 利用这一原理，使得方言间的 Lowering 成为解释器特化的副产品。

### 5.4 统一性定理

**定理 4（Nyar 完备性）**：对于任何具有对象代数接口的语言 $\mathcal{L}$，存在 Nyar 工厂实现，使得：

1. EGgraph 构建器能产生包含所有重写闭包的优化表示。
2. PE 构建器能产生自动 Lowering 转换器。
3. 所有其他操作（求值、打印、分析）可由同一接口的不同实现提供。

因此，Nyar 从理论上覆盖了编译器和语言工具链所需的全部分维。

## 第六章 Nyar 的实现蓝图与工程落地

本章阐述如何将上述理论落地为现实可用的工具，尤其强调如何利用 Source Generator 弥补理想类型系统与现实 C# 的差距。

### 6.1 方言定义：以声明驱动

Nyar 提供 `[Dialect("name")]` 和 `[Operator("op")]` 属性（Attribute），开发者只需定义接口：

```csharp
[Dialect("arith")]
public partial interface IArith
{
    [Operator("const")] Term<int> Const(int v);
    [Operator("add")] Term<int> Add(Term<int> a, Term<int> b);
}
```

这里的 `Term<T>` 是标记类型，用于元生成器识别。真实运行时它会被擦除。

### 6.2 元生成器：一次定义，全部派生

Nyar 的 Source Generator（源生成器）分析上述接口，在编译时生成：

- **泛型代数接口** `IArithAlg<E>`：将 `Term<T>` 替换为 `E`。
- **AST 节点**（可选）：`ConstNode`, `AddNode` 等。
- **EGraph 构建器** `ArithEgraphBuilder : IArithAlg<Id>`：每个方法映射到 EGraph 插入操作。
- **部分求值构建器** `ArithPEBuilder : IArithAlg<(bool, object?, object?)>`：实现静态折叠逻辑。
- **IKun 桥接器**：生成强类型 IR 节点构造。
- **模式匹配器**：为规则 DSL 生成强类型辅助方法。
- **PSI 构建器**：生成带源位置信息的语法树构造器。
- **分析器骨架**：生成类型检查、Lint、格式化的抽象基类。

所有这些生成都实现了相同的 `IArithAlg<E>` 接口，因此它们是可互换的。用户只需在特定基类中补充具体逻辑（如重写规则、成本模型）。

### 6.3 方言注册与组合

运行时，所有方言的 `IDialect` 实现注册到 `DialectRegistry`，该注册表验证 Lowering 依赖关系，并提供拓扑排序。
`CompositeDialect` 将多个方言的规则、成本模型合并，创建统一的饱和优化环境。

### 6.4 处理现实 C# 的类型限制

由于 C# 缺乏 higher-kinded types 和 associated types，生成器采取以下降级策略：

- 将 `Expr<T>` 全部擦除为单一 `E`，在工厂内部通过约定的 `IKun` 节点层级保持类型安全。
- 利用分部类和抽象基类提供“类型安全的包装层”，将 `E` 转换为具体类型并在开发时提供编译期检查，尽量挽回静态安全性。

## 第八章 未来展望：从元编译器到元语言工程

Nyar 打开了一扇通向“元语言工程”的大门。未来方向包括：

- **可视化规则编辑**：在一个图形界面中，为方言添加等价规则，实时观察 EGraph 的饱和过程和成本提取。
- **增量 EGraph**：支持 IDE 中代码修改时只重新饱和受影响的子图，提供实时优化反馈。
- **形式验证集成**：将重写规则作为定理，利用证明助手（如 Coq）验证其语义保持性，再导入 Nyar。
- **分布式编译**：EGraph 的饱和过程可以基于无锁的并行算法，扩展到大规模代码库。
- **自适应优化策略**：成本模型本身可以作为学习参数，通过强化学习自动调整规则权重。

Nyar 不是终点，而是迈向真正智能、自动化语言工具链的起点。

## 第九章 结论：唯一的答案

编译器领域长期徘徊在工程经验主义的黑暗森林中。LLVM 的人肉维护、MLIR 的语法优先歧途、GraalVM
的封闭妥协，都证明了同一个真理：没有第一性原理的道路是不可持续的。编程语言理论经过半个世纪的洗礼，终于揭示了对象代数、等式饱和与部分求值这三大第一性原理。它们分别解决了“如何表示”、“如何优化”和“如何转换”这三个根本问题。

Nyar 是三大原理的首次工业级融合。它宣告了编译器设计中“人肉承担一切”旧时代的终结。在 Nyar
范式下，语言是可组合的接口，优化是声明式的等价探索，转换是自动的语义推导。表达式问题被彻底终结，编译器工具链第一次成为真正可无限扩展的有机系统。

**Nyar 不是众多选项中的一个，而是理论必然性所指向的唯一答案。**

未来的编译器，即便不是 Nyar，也必将在这个新的地基上重建。
