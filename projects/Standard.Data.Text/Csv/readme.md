# CSV 序列化器

## 定位

CSV 序列化器实现 `ISerializer`，将对象转为 CSV 文本。它是 Sonic.Data 的 **表格数据导出格式**。

## 为什么需要 CSV？

两个场景 JSON 做不好：

1. **Excel 用户**：CSV 是 Excel 的原生导入格式。当你需要把数据库查询结果导出给业务人员时，发送一个 JSON 文件等于发送了一份"
   请先写个脚本解析"的作业。CSV 双击打开即可。

2. **流式大数据处理**：CSV 的逐行独立性使得你可以逐行写、逐行读，不需要在内存中维护整个文档的嵌套结构。处理 10GB 的 CSV
   日志文件，你可以一行一行过。处理 10GB 的 JSON 数组，你必须在顶层维护 `[` 未闭合的上下文。

## CSV 的设计取舍

CSV 不是一个"格式标准"——RFC 4180 只是约定，不同工具对转义、分隔符、表头的处理各不相同。Sonic CSV 序列化器的取舍是：

- **第一行输出表头**。这与 Excel 导入行为一致，也是大多数数据分析工具（pandas、R）的期望。
- **逗号分隔**。制表符（TSV）在某些欧洲地区更流行（逗号在当地是小数点），但全局默认还是逗号。
- **Base64 编码二进制**。CSV 是纯文本格式，二进制字段不能直接嵌入。Base64 是最通用的文本化方案。
- **不支持嵌套对象**。这是 CSV 的根本限制。如果你的数据有嵌套（`Person.Address.City`），用 JSON，不要用 CSV。

## 不应该承担什么职责？

- **不应做 Excel 公式兼容**：CSV 不区分 `=SUM(A1:A10)` 和字符串 `"=SUM(A1:A10)"`。这是 Excel 的问题，不应由序列化器解决。
- **不应实现 CSV 解析器**：反序列化方向（CSV → 对象）远比序列化方向复杂——需要处理不同方言（分隔符、引号、换行符内的换行）。当前只实现写方向。

## 典型场景

- **数据导出**：`List<Order>` → CSV → 下载给运营同事。
- **日志流水**：每行一个 CSV 记录（带时间戳），逐行追加到文件。
