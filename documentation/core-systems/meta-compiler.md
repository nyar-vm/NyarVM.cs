# 元编译器

## 什么是元编译器

传统编译器针对**特定源语言**和**特定目标机器**。元编译器接受**任意语言的意图表示（OA 程序函数）**、**一组优化规则**和**成本模型**，生成一个**针对该语言和目标的专用编译器**。

在 Nyar 中，元编译器本身由一组 OA 工厂实现组成。整个编译过程是：**同一段程序函数，依次传入不同的工厂实例，每个工厂完成一个阶段的处理。**

## OA 编译管线

```
源语言代码
   │
   ▼  ┌─────────────────────────────────────────┐
   │  │ 前端：源语言 → OA 程序函数                 │
   │  │ (外部提供，通常是 Oak 的 Parser)           │
   │  └─────────────────────────────────────────┘
   │
  OA 程序函数: static E P<IDialectAlg<E>>(IDialectAlg<E> alg) => ...
   │
   ├──► 传入 EGraph 工厂 ──► 构建 EGraph，饱和优化
   │         E = EClassId
   │
   ├──► 传入 PE 工厂 ──► 特化静态已知部分，生成残余代码
   │         E = (bool Static, object Val, object? Residual)
   │
   ├──► 传入成本模型 ──► 从等价类中选择最优表示
   │         E = CostVector
   │
   ▼
  最优表示（可能是 AST、EGraph 提取结果、PE 特化版本）
   │
   ▼  ┌─────────────────────────────────────────┐
   │  │ 后端：最优表示 → 目标代码                  │
   │  │ (OA 工厂: E = 目标平台数据结构)            │
   │  └─────────────────────────────────────────┘
   │
 目标代码（.nyar / .class / .wasm / .exe / ...）
```

关键特性：**程序函数在整条管线中保持不变**。改变的不是程序，而是传入的工厂。这意味着：
- 管线可重排：可以先 PE 再 EGraph，也可以先 EGraph 再 PE
- 管线可增量：EGraph 的饱和可以增量更新，PE 可以缓存特化结果
- 管线可并行：不同工厂对同一程序的调用可以并发执行

## 元编译器架构

```
      语言前端 (外部提供)            Nyar 元编译器核心                后端 (外部或内置)
    ┌─────────────────┐     ┌────────────────────────────┐      ┌─────────────────┐
    │  源语言代码      │     │  OA 工厂实现（四个阶段）      │      │  NyarVM         │
    │  ↓              │     │                            │      │  ↓              │
    │  Parser → OA    │────►│  1. EGraph 构建器           │      │  解释器/JIT     │
    │  程序函数        │     │     EClassId                │      └─────────────────┘
    └─────────────────┘     │                            │
                            │  2. 饱和引擎 + 重写规则     │      ┌─────────────────┐
                            │     EGraph.Saturate()       │      │  JVM 后端       │
                            │                            │───► │  (.class)      │

                            └────────────────────────────┘      └─────────────────┘
                                                                      │
                                                                      ▼
                                                               ┌─────────────────┐
                                                               │  Native 后端    │
                                                               │  (x86/ARM/RISC-V)│
                                                               └─────────────────┘
```

## 重写规则

### OA 规则引擎

重写规则也是可扩展的 OA 结构：

```csharp
public interface IRewriteRule<Alg> where Alg : class
{
    void Register(RewriteEngine<Alg> engine);
}

// 常量折叠规则
public class ConstantFoldRule : IRewriteRule<ICoreAlg<EClassId>>
{
    public void Register(RewriteEngine<ICoreAlg<EClassId>> engine)
    {
        // Add(0, x) → x
        engine.Rule(alg => alg.Add(alg.Int32(0), alg.Any<int>()))
              .Replace((_, x) => x);

        // Mul(1, x) → x
        engine.Rule(alg => alg.Mul(alg.Int32(1), alg.Any<int>()))
              .Replace((_, x) => x);

        // If(true, x, y) → x
        engine.Rule(alg => alg.If<bool>(alg.Bool(true), alg.Any<bool>(), alg.Any<bool>()))
              .Replace((_, x, _) => x);
    }
}
```

规则可以来自方言库，也可以由用户编写。`alg.Any<T>()` 是模式变量，比字符串通配符更精确且类型安全。

### 规则分类

| 类别 | 说明 | 示例 |
|:---|:---|:---|
| **代数规则** | 结合律、交换律、分配律 | `Add(a,b) ≈ Add(b,a)` |
| **领域特定规则** | 方言级的语义融合 | `Conv2D+BN+ReLU → FusedConvBNReLU` |
| **目标特定规则** | 利用目标架构特性 | `Mul(a,2) → ShiftLeft(a,1)`（x86 LEA 优化） |
| **推测规则** | 基于概率的变换 | 分支预测重排 |

## 与部分求值（PE）的协同

部分求值在 Nyar 中是 OA 管线的**一个工厂阶段**，而非独立 Pass：

1. **PE 识别静态部分**：分析程序函数，找到编译时已知的参数
2. **生成特化版本**：为静态参数生成特化的工厂调用
3. **加入 EGraph**：特化版本与通用版本共存于同一等价类
4. **成本模型决策**：比较特化版的加速收益 vs 代码膨胀代价

```csharp
// pow(x, 2) 在 x 静态已知时 → 直接常量
// 在 x 为变量时 → x*x → 加入 EGraph，与通用 pow 共存
// 成本模型根据上下文选择最优版本
```

## 广义优化案例集

Nyar 的元编译器不限定领域——任何能用 OA 表达的计算都可以优化。

### 案例 A：正则表达式优化

正则 `a(b|c)*d` 转为 OA 程序函数。优化规则包括：
- `Alt(a, b)` → `CharClass([ab])`
- `Seq(Star(Alt(a,b)), c)` → `Star(Alt(Seq(a,c), Seq(b,c)))`
- 根据输入特征选择 DFA 或 NFA

### 案例 B：SQL 查询优化

意图：`Join(Scan(R), Scan(S), condition)`。规则枚举 Join 顺序、下推谓词、选择索引扫描。成本模型利用统计信息估计 IO 和 CPU。

Nyar 的优势：可以跨领域融合。如果查询包含 ML 模型调用（UDF），优化器可尝试将模型推入 Scan 算子，实现**数据库内推理**。

### 案例 C：芯片设计高层综合

意图：`ConvLayer(input, weights, stride)`。优化规则降级为循环嵌套、流水线或脉动阵列。PE 特化固定参数（如 stride=2），生成无分支的硬件描述。输出 Verilog 或 C++ 仿真模型。

## 元编译器的意义

元编译器不是取代现有优化器，而是**统一优化范式**，让不同领域共享：

- **等价推理引擎**：无需为每个领域重新发明 EGraph
- **OA 工厂框架**：同一方言接口驱动编译、分析、IDE、扫描
- **成本模型框架**：可组合、可学习
- **多目标降级**：高层意图可逐步降低到不同后端

一个数据库开发者无需成为编译原理专家，只需提供关系代数的 OA 接口和重写规则，Nyar 就能生成一个查询优化器。
