# 中间件与上层建筑

> Layer 3：建立在状态管理之上的洋葱模型、微服务、API 网关等。

## 为什么叫"上层建筑"

上一章讲了 Layer 1（状态管理）是底层，基础不牢地动山摇。那么中间件、洋葱模型、微服务这些东西是什么？

**它们是上层建筑。** 它们解决的是请求如何到达状态管理层、如何被加工、如何被路由的问题，而不是状态本身如何管理的问题。

```
┌─────────────────────────────────────────────────────────┐
│  请求进入                                                │
│  ↓                                                      │
│  ┌─────────────────────────────────────────────────────┐│
│  │  Layer 3: 上层建筑                                   ││
│  │                                                     ││
│  │  ┌───────────┐  ┌──────────┐  ┌──────────────────┐ ││
│  │  │ API 网关   │  │ 认证授权  │  │ 限流/熔断/降级   │ ││
│  │  └───────────┘  └──────────┘  └──────────────────┘ ││
│  │  ┌───────────┐  ┌──────────┐  ┌──────────────────┐ ││
│  │  │ 路由      │  │ 日志追踪  │  │ 请求/响应转换    │ ││
│  │  └───────────┘  └──────────┘  └──────────────────┘ ││
│  │                                                     ││
│  │  洋葱模型：请求穿过多层中间件 → 到达业务逻辑 → 返回   ││
│  └──────────────────────────┬──────────────────────────┘│
│                             ↓                            │
│  ┌──────────────────────────┴──────────────────────────┐│
│  │  Layer 2: 服务控制反转                               ││
│  │  Sonic.Use<T>() / Schema 自动注册                    ││
│  └──────────────────────────┬──────────────────────────┘│
│                             ↓                            │
│  ┌──────────────────────────┴──────────────────────────┐│
│  │  Layer 1: 状态管理（底层）                            ││
│  │  Persistent / Ephemeral                              ││
│  └─────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────┘
```

上层建筑可以替换、可以增减、可以重组，但底层不能动摇。你可以从 REST 换成 gRPC，从单体换成微服务，从 Express 换成 Kestrel——但 Persistent/Ephemeral 二分不变。

## 洋葱模型

洋葱模型是 ASP.NET Core 的核心请求处理模式，也是 Sonic 上层建筑的基础组织方式：

```
                    请求 →
                      │
        ┌─────────────┼─────────────┐
        │  中间件 1（日志）           │
        │  ┌─────────────┼─────────┐│
        │  │  中间件 2（认证）       ││
        │  │  ┌───────────┼───────┐││
        │  │  │  中间件 3（限流）   │││
        │  │  │  ┌─────────┼─────┐│││
        │  │  │  │  业务逻辑  ││││
        │  │  │  │  读写状态  ││││
        │  │  │  └─────────┘││││
        │  │  └───────────┘│││
        │  └─────────────┘││
        └─────────────┘│
                      │
                    ← 响应
```

每一层中间件都可以在请求到达业务逻辑之前和之后执行逻辑：

- **之前：** 日志记录、认证检查、限流判断
- **之后：** 响应压缩、异常处理、追踪关闭

**洋葱模型与状态管理的关系：** 中间件可以读写状态，但必须遵守 Persistent/Ephemeral 的规则。例如：
- 认证中间件可以从 Cache 读取会话（Ephemeral 加速），但会话创建必须写入 Database（Persistent）
- 限流中间件可以从 State 读取计数器（Ephemeral），但限流策略配置必须从 Database 读取（Persistent）

## 微服务

微服务是一种部署架构，不是一种编程范式。从状态管理的角度看，微服务的核心问题是：

> **如何划分 Persistent 的边界？**

```
单体架构：
┌──────────────────────────────────────┐
│  用户服务 ──→ Database A             │
│  订单服务 ──→ Database A             │  ← 共享 Database
│  商品服务 ──→ Database A             │
└──────────────────────────────────────┘

微服务架构：
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  用户服务     │  │  订单服务     │  │  商品服务     │
│  Database A  │  │  Database B  │  │  Database C  │  ← 独立 Database
└──────────────┘  └──────────────┘  └──────────────┘
       │                 │                 │
       └────────┬────────┘────────┬────────┘
                ↓                 ↓
           Stream（事件）     Storage（文件）
```

**微服务的本质是 Persistent 的拆分。** 每个微服务拥有自己的 Persistent 层（Database + Storage），服务间通过 Stream 通信。Ephemeral 天然是实例私有的，不需要拆分。

**Sonic 对微服务的态度：** Sonic 支持微服务部署，但不强制。单体也好，微服务也好，Persistent/Ephemeral 二分不变。你可以从单体开始，在需要时拆分 Persistent 边界。

## API 网关

API 网关是上层建筑中的路由层：

```
客户端 → API 网关 → 用户服务
                  → 订单服务
                  → 商品服务
```

网关的职责：
- **路由：** 请求分发到正确的后端服务
- **认证：** 统一的 JWT/OAuth 验证
- **限流：** 保护后端不被过载
- **聚合：** 多个后端响应合并为一个

**网关与状态管理的关系：** 网关本身不持有 Persistent 状态。它可能使用 Ephemeral（如限流计数器、JWT 黑名单缓存），但这些状态的丢失不影响系统正确性。

## 认证授权

认证授权是上层建筑中的安全层：

```
请求 → 认证中间件 → 授权中间件 → 业务逻辑
         │              │
         ↓              ↓
    验证 Token      检查权限
    (Ephemeral     (Persistent
     Cache 加速)    Database)
```

- **认证（Authentication）：** 验证"你是谁"——JWT 验证、Session 查找
- **授权（Authorization）：** 验证"你能做什么"——角色/权限检查

**与状态管理的关系：**
- JWT 是无状态的，不需要服务端存储（纯计算，不涉及状态管理）
- Session 是有状态的，Session 数据存 Persistent，Session 查找可用 Ephemeral 加速
- 权限数据存 Persistent，权限检查可用 Ephemeral 加速

## 其他中间件

| 中间件 | 职责 | 使用的状态 |
|--------|------|-----------|
| 日志 | 请求/响应记录 | Ephemeral（缓冲）→ Persistent（归档） |
| 追踪 | 分布式链路追踪 | Ephemeral（Span 缓冲） |
| 限流 | 请求频率控制 | Ephemeral（计数器） |
| 熔断 | 故障隔离 | Ephemeral（状态机） |
| CORS | 跨域控制 | 无状态（纯配置） |
| 压缩 | 响应压缩 | 无状态（纯计算） |

## 设计原则

1. **上层建筑不改变底层的语义。** 无论中间件怎么组合，Persistent 始终是真相来源，Ephemeral 始终是加速副本。
2. **上层建筑可以替换。** 从 REST 换成 gRPC，从单体换成微服务——底层不变。
3. **上层建筑的复杂度是可选的。** 你可以从零中间件开始，按需添加。但底层（状态管理）从第一天就必须正确。
4. **中间件的状态使用必须遵守规则。** 中间件可以读写状态，但必须遵守 Persistent/Ephemeral 二分原则。
