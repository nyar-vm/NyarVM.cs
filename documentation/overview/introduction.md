# 什么是后端

## 剥去一切，后端的本质是什么？

REST API？微服务？洋葱模型？中间件管道？数据库？

都不是。剥去一切花哨的概念，后端最本质的工作只有一件事：

> **管理状态的生命周期。**

请求进来，读状态、写状态、转移状态。所有的业务逻辑，归根结底都是状态转换规则。所有的后端架构，归根结底都是状态管理的组织方式。

- 用户注册？创建一条用户状态
- 下单？创建一条订单状态，修改库存状态
- 发消息？创建一条消息状态，推送通知状态
- 查询？读取状态，可能经过缓存加速

**后端即状态管理。** 这不是比喻，这是定义。

## 状态管理的两个世界

状态不是铁板一块。从生命周期的角度看，状态天然分为两类：

### Persistent — 持久化

```
特征：中心化访问，跨实例唯一，数据是真相来源
语义：写入即承诺，数据不会因实例重启或销毁而丢失
```

持久化是后端的根基。用户数据、订单记录、文件资产——这些状态必须跨实例共享，是整个系统的真相来源（Source of Truth）。

### Ephemeral — 临时状态

```
特征：sidecar 加载，随实例生灭，数据是加速副本
语义：丢失可接受，数据可以从持久化层重建
```

临时状态是后端的加速器。会话缓存、查询结果缓存、本地计算中间态——这些状态只服务于当前实例，实例销毁后数据随之消失，不会影响系统正确性。

### 关键洞察：这是用法，不是技术

**同一个技术，两种用法，两种语义：**

| 技术 | 中心化用 = Persistent | sidecar 加载 = Ephemeral |
|------|----------------------|--------------------------|
| Redis | 共享缓存集群，跨实例读写 | 容器内 sidecar，仅本实例可见 |
| SQLite | NFS 共享数据库文件 | 容器内本地文件 |
| LevelDB | 共享存储挂载 | 容器内本地盘 |

Sonic 的选择：**Redis 作为 Ephemeral（sidecar 模式），不作为 Persistent。** 这不是技术限制，而是架构原则——缓存和持久化的语义必须分离，否则系统的状态一致性就建立在沙子上。

## Sonic 的定位

Sonic 是以状态管理为底层、Persistent/Ephemeral 二分为原则的后端基础设施。

它不试图发明新的技术，而是**用正确的概念组织已有的技术**：

```
┌─────────────────────────────────────────────────────┐
│              状态管理（State Management）              │
│                                                     │
│  ┌──────────────────────┐  ┌──────────────────────┐ │
│  │   Persistent（持久化）│  │  Ephemeral（临时状态） │ │
│  │                      │  │                      │ │
│  │  中心化，跨实例唯一    │  │  sidecar，随实例生灭   │ │
│  │  数据是真相来源       │  │  数据是加速副本       │ │
│  │                      │  │                      │ │
│  │  ┌────────────────┐  │  │  ┌────────────────┐  │ │
│  │  │ 结构化（Table） │  │  │  │ 内存（Memory）  │  │ │
│  │  └────────────────┘  │  │  └────────────────┘  │ │
│  │  ┌────────────────┐  │  │  ┌────────────────┐  │ │
│  │  │ 文件（File）    │  │  │  │ 本地盘（Local） │  │ │
│  │  └────────────────┘  │  │  └────────────────┘  │ │
│  │  ┌────────────────┐  │  │                      │ │
│  │  │ 瞬态（Queue）   │  │  │                      │ │
│  │  └────────────────┘  │  │                      │ │
│  └──────────────────────┘  └──────────────────────┘ │
└─────────────────────────────────────────────────────┘
```

**基础不牢，地动山摇。** 状态管理是底层，中间件、洋葱模型、微服务都是上层建筑。底层概念清晰，上层自然稳固；底层概念混乱，上层再花哨也是空中楼阁。
