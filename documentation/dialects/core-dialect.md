# Core 方言

## 设计原则

Core 方言是 Nyar IR 的"宪法"，一旦确定，将深刻影响未来十年所有方言的设计。一个冗余的节点会让优化器臃肿，一个缺失的节点则会让某些语言特性沦为二等公民。

Core 方言必须满足三个条件：

- **不可归约性**：无法用其他 Core 节点表达的语义原子
- **跨方言通用性**：几乎所有上层方言都需要依赖的基础操作
- **优化无关性**：其语义足够清晰，不预设特定优化策略，但能为优化提供锚点

## 15 个语义原子

经过严格审查，Nyar Core 方言仅包含以下 15 个不可再分的语义原子：

### 值

| 节点 | 语义描述 | 效应 |
|------|----------|------|
| Literal | 携带一个编译时已知的值（整数、浮点、布尔、类型句柄等） | 纯 |

### 纯运算

| 节点 | 语义描述 | 效应 |
|------|----------|------|
| Add, Sub, Mul, Div, Rem | 无限精度算术运算（语义由类型标签决定） | 纯 |
| Neg, Not | 一元算术/逻辑非 | 纯 |
| Cmp (带比较码：Eq, Ne, Lt, Le, Gt, Ge) | 比较两个值，返回布尔 | 纯 |

### 数据聚合

| 节点 | 语义描述 | 效应 |
|------|----------|------|
| Tuple | 将多个值打包为一个匿名结构 | 纯 |
| Project | 从 Tuple 中提取第 N 个元素 | 纯 |

### 内存

| 节点 | 语义描述 | 效应 |
|------|----------|------|
| Alloc | 分配指定字节数的未初始化内存块，返回指针 | 分配 |
| Free | 释放之前分配的内存块 | 分配 |
| Load | 从内存地址读取值（可带原子序） | 读 |
| Store | 向内存地址写入值（可带原子序） | 写 |

### 控制流

| 节点 | 语义描述 | 效应 |
|------|----------|------|
| Label | 标记一个基本块的开始 | 控制 |
| Branch | 条件或无条件跳转到另一个 Label | 控制 |
| Phi | 根据进入边选择值 | 控制 |
| Call | 调用一个函数（目标为另一意图入口），创建栈帧 | 控制 |
| Return | 从当前函数返回一个值 | 控制 |

### 效应

| 节点 | 语义描述 | 效应 |
|------|----------|------|
| Perform | 引发一个代数效应，将控制转移给最近的处理器 | 效应 |
| Handle | 安装一个效应处理器，作用域覆盖其子意图 | 效应 |

## 关键设计决策

### 为何保留二元运算而非全部用 Call

如果 Core 只有 Call，那么 `(+ a b)` 就是一个调用目标未知的函数。优化器将完全无法进行代数化简，因为无法知道 `+` 是否满足交换律、结合律。

Core 必须提供一组语义明确的、无副作用的、纯数学运算，作为代数重写的锚点。

**如何处理重载与语言差异？**

- 类型标注驱动：Add 节点携带精确的 TypeAnnotation（如 I32 或 F64 或 String）。重写规则仅当类型匹配时才生效
- 溢出语义：作为方言扩展。Core 的 Add<I32> 默认行为是无限精度数学加法，重写规则基于数学定律。当降级到具体后端（如 x64）时，才根据目标语言的溢出语义插入 CheckedAdd 或 WrappingAdd 节点

### 为何没有 Const 节点

不同语言对"常量"的定义不同。C 的 `const int` 是编译时常量；Java 的 `String` 字面量是运行时常量池索引；Python 的 `(1,2)` 是可变还是不可变？

解决方案：Core 方言不应包含 Const 节点。取而代之，每个 IntentNode 应有一个可选的 ValuePayload 字段。如果节点表示一个已知值（如整数 42），它是一个带有 `ValuePayload(42)` 的 Literal 操作符。

### 为何没有 New/Box 等 GC 相关节点

Core 必须能描述冯·诺依曼机器的本质：可寻址内存、读写、分配/释放。否则无法表达任何底层状态修改。

- Alloc vs New：Alloc 是未初始化的内存块分配。New 是带构造函数的对象分配，属于语言运行时方言
- GC 的抽象：GC 不是一种操作，而是一种内存管理策略。Core 方言不规定如何回收，只规定何时不可达（通过 Free 显式释放或依赖运行时分析）

### 为何 Fence 不作为独立节点

Fence 属于内存模型，是目标相关约束，不应污染 Core。作为 Load/Store 节点的 MemoryOrder 属性存在。

## 关键元数据字段

每个节点都拥有以下元数据：

- **TypeAnnotation**：静态类型信息，可携带依赖证明
- **EffectSet**：由操作符自动推导，也可由前端显式标注
- **MemoryOrder**：仅对 Load/Store 有效（None, Acquire, Release, SeqCst）
- **LocationHint**：调试信息

## 为何这样设计能应对兼容性与未来挑战

- **极简核心**：15 个节点是任何图灵完备计算模型的最小集合。未来任何新特性都可以用这 15 个节点组合表达，或通过方言扩展
- **类型驱动重载**：二元运算不区分整数/浮点/字符串，类型标签决定了重写规则的可用性。新增一种可交换的类型（如复数）只需在类型系统中注册，并添加对应规则，无需修改 Core
- **GC 的分离**：Core 只关心语义上的内存操作，不关心策略上的回收。GC 语言前端可以不生成 Free，Nyar VM 的 GC 会接管
- **效应作为逃生舱**：任何未来出现的奇怪控制流（如 call/cc、生成器、逻辑变量），都可以通过扩展效应类型来支持，而无需修改 Core 的控制流节点
